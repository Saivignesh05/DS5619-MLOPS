## Background

The batch-scoring DAG has this shape (the “anatomy of a DAG” from the lecture, applied):

```text
extract --> score --> load
                  \-> notify
```

- `extract`: list every image under `data/fixtures/`.
- `score`: run the detector over each image, accumulate detection counts.
- `load`: write `batch_report.json` — depends only on `score`.
- `notify`: a deliberately FLAKY task (fails twice, then succeeds) standing in for something like a webhook call — also depends only on `score`. It exists so your retry logic actually gets exercised by a real DAG run, not just by unit tests.

## Implementation and files involved

The implementation belongs in `src/mini_orchestrator.py`. The other provided pipeline files are used by the orchestrator but should not need modification.

### 1. `topological_order(tasks)`

This function calculates a valid task order using Kahn's algorithm:

1. Calculate each task's in-degree from its dependencies.
2. Build a list of tasks that depend on each task.
3. Start with tasks that have no dependencies.
4. Process those tasks and reduce the in-degree of their dependent tasks.
5. Add a dependent task to the ready list when all its dependencies have been processed.
6. Raise `ValueError` if a dependency names a task that does not exist or if a cycle prevents all tasks from being ordered.

This supports branching DAGs, such as the `load` and `notify` sibling tasks in this assignment.

### 2. `run_task_with_retry(task, context)`

This function runs one task and handles temporary failures:

1. Execute the task with the shared `context` dictionary.
2. If it succeeds, return the number of attempts used.
3. If it raises an exception and retries remain, wait for `retry_delay_seconds` and try again.
4. If all allowed attempts fail, re-raise the final exception.

`max_retries` counts additional attempts after the initial attempt. For example, `max_retries=2` allows up to three total attempts.

### 3. `run_dag(tasks, context)`

This function coordinates execution of the DAG:

1. Obtain the dependency-respecting order from `topological_order`.
2. Run tasks in that order, passing the same context dictionary to each task.
3. Record each task's status and attempt count.
4. If a task fails after its retries are exhausted, record the failure and stop the run rather than executing later tasks.
5. Return the execution order and task results for the driver to write to `dag_run_summary.json`.
